# 音频设置与监控

[返回中文说明](README.zh-CN.md)

在“设备”页连接 Android，在“音频设置”页选择采集来源、格式和缓冲，在“实时监控”页查看运行状态。音频设置会保存，并在下次连接时生效；连接和传输期间需要先断开才能修改。

## 采集来源与音质

- Windows 支持系统输出回环和录音输入，可选择物理或虚拟音频端点。“跟随系统默认”在连接时确定设备；采集端点失效会结束连接并报告错误。
- macOS 使用 ScreenCaptureKit 采集系统音频，当前不提供录音输入设备选择。
- 两端均发送未压缩的双声道 PCM16 或 Float32。Windows 使用采集端点的混音采样率，macOS 使用 48 kHz。单声道复制为双声道；多声道按声道掩码下混并排除 LFE。
- Float32 避免统一量化为 16 位，但系统混音、声道转换和播放处理仍可能改变采样。未压缩传输不代表源文件到扬声器逐位一致。

捕获系统声音不需要额外安装虚拟声卡。已有虚拟端点可以用于应用路由或混音；选中物理扬声器进行回环采集时，电脑仍会正常播放该端点上的声音。

## 缓冲设置

默认使用“均衡”档位。切换档位会保留已选采集来源、设备和格式，并开启低延迟输出请求。

| 档位 | 播放缓冲目标 | 启动预填充 | 接收数据块 | 采集队列上限 |
| --- | ---: | ---: | ---: | ---: |
| 低延迟 | 20 ms | 10 ms | 2 ms | 20 ms |
| 均衡 | 40 ms | 10 ms | 5 ms | 60 ms |
| 稳定 | 100 ms | 40 ms | 10 ms | 160 ms |

手动修改后显示“自定义”：

| 设置 | 范围 | 含义 |
| --- | --- | --- |
| 播放缓冲目标 | 10-500 ms | 请求 Android 使用的有效播放缓冲，实际值受设备限制 |
| 启动预填充 | 0-250 ms，且不超过播放缓冲目标 | 开始播放前写入的音频量 |
| 接收数据块 | 1-40 ms | 每次读取的上限，收到完整帧即可处理，不等满整个块 |
| 采集队列上限 | 10-500 ms | 电脑采集与发送线程之间允许积压的音频量 |

“请求低延迟输出”由 Android 决定是否接受，监控显示实际输出模式。Android 8 及以上会请求低延迟性能模式，Android 12 及以上还会设置启动阈值。

开启此选项时，Android 7 及以上会根据新增欠载逐步增加有效播放缓冲，最大不超过设备分配的容量；扩容时会短暂停播并补充缓冲。实际未获得低延迟模式的设备，以至少 32 ms 的缓冲和启动预填充起步，并受实际容量限制。获得低延迟模式的设备保留请求值。关闭该选项会禁用自动扩容；Android 6 使用平台默认的有效缓冲管理。

采集队列与 Android 接收队列均有容量上限，溢出时按完整帧丢弃旧音频，以减少持续积压。Android 接收队列默认上限为标准模式 40 ms、低延迟模式 12 ms，并至少容纳两个接收块。队列追帧可能发生在启动或过载时，不能保证全程保留每一个采样。

## 监控指标

| 指标 | 含义 |
| --- | --- |
| 声道电平 | 左右声道的峰值与 RMS，单位为 dBFS |
| 传输速率 | 按实际发送字节数计算的音频负载速率 |
| 采集队列 | 电脑上等待发送的音频时长 |
| 播放队列估计 | Android 已写入 AudioTrack 的帧数减去已播放帧数所对应的时长 |
| 丢弃帧数 / 采集中断次数 | 电脑采集队列丢弃的帧数，以及采集端报告的不连续次数 |
| 播放欠载次数 | Android 播放缓冲未得到及时补充的累计次数；不支持时显示不可用 |
| 实际播放缓冲 / 输出模式 / 播放设备 | Android 返回的有效缓冲、性能模式及输出路由 |

桌面每 500 ms 采样一次，图表保留最近 120 个样本。暂停只冻结图表显示，传输和后台统计继续；清空只删除图表历史，不重置本次连接的累计计数。Android 反馈超过 3 秒未更新时，当前播放指标显示不可用，历史曲线在缺少反馈的位置断开。

播放队列估计不包含 Android 接收队列、ADB 中间缓冲、系统输出和声学链路。缓冲容量、当前排队时长与端到端延迟应分别理解；确认实际听感延迟需要单独回录或声学测量。

## 常见问题

- **低延迟档断续**：观察欠载是否持续增加，断开后改用均衡或稳定档，或适当增加播放缓冲。目标值越小，设备越可能无法稳定补充音频；以实际缓冲和欠载变化判断效果。
- **延迟仍然明显**：先检查采集和播放队列是否持续积压，再比较 Android 输出路由和 USB / Wi-Fi 连接。降低采集队列上限会增加追帧机会，无法消除系统输出链路中的全部延迟。
- **启动或连接失败**：保留完整应用目录，并确认 Android 已授权 USB 调试。Windows 运行目录应包含引擎、采集 DLL、ADB、`server` 和 `data` 资源；桌面客户端、原生库与 Android 服务需要一起更新。
- **关闭与断开**：正常关闭 Windows 窗口会停止音频、取消本会话的 ADB 命令并清理专用隧道，保留共享 ADB 服务。强制结束进程或拔线可能中断清理。

## Windows 本机预览

标准发布构建见 [中文说明](README.zh-CN.md#从源码构建)。已有 MinGW、Flutter Windows 引擎缓存、C++ wrapper 和插件链接的环境，也可以使用预览脚本；脚本不负责初始化完整的 Flutter Windows 构建环境。

从仓库根目录执行，以下工具链路径需要替换为本机路径：

```powershell
.\tools\build_android_preview.ps1 `
    -JavaHome 'C:\path\to\jdk' `
    -AndroidJar 'C:\path\to\android.jar' `
    -D8Jar 'C:\path\to\d8.jar'

.\tools\build_windows_preview.ps1 `
    -FlutterSdk 'C:\path\to\flutter' `
    -MinGWRoot 'C:\path\to\mingw64'
```

Android 预览脚本编译 DEX JAR 并更新 `client/assets/server`；Windows 脚本使用该资源，不会自动重建 Android 服务。`-SkipAssets` 仅适用于 Dart 和资源均未变化、只需重建原生部分的情况。

预览入口为 `client/build/preview/windows/audioshare.exe`，需要保留整个 `windows` 目录。运行环境需要 Visual C++ 运行库。重新构建前先关闭预览，runner 编译日志位于 `client/build/preview/runner-build.log`。

## 真机验证

`tools/verify_audio_device.py` 支持原生库检查、Android 静音播放测试和完整 Windows 采集链路测试。从仓库根目录执行以下命令，并将设备序列号替换为 `adb devices` 中的值；测试期间关闭桌面应用，单独连接测试设备：

```powershell
python .\tools\verify_audio_device.py `
    --bridge --no-keepalive `
    --native .\client\build\preview\windows\audio_capture.dll `
    --adb .\client\assets\adb.exe `
    --server .\client\assets\server `
    --serial '<设备序列号>' `
    --duration 60 --bits 16 32 `
    --buffer-ms 20 --pre-roll-ms 10 --read-chunk-ms 2 --queue-ms 20
```

`--native <dll>` 单独检查采集 ABI、格式、端点错误和停止竞态；`--adb <adb> --server <server> --serial <id>` 单独检查 Android 接收与播放。完整链路测试使用 `--bridge`；`--no-keepalive` 关闭额外的测试保活输出，用于检查应用自身维持回环采集的能力。

报告区分启动阶段、稳态新增欠载和丢帧、队列估计，以及原生停止和 Android 退出耗时；稳态统计排除最初 2 秒。启动阶段丢帧仍计入累计值。脚本使用专用设备文件与反向隧道，结束时清理；队列和呈现进度的估计不能作为声学端到端延迟。
